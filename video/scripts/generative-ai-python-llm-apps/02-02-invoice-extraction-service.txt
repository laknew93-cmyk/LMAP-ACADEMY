Welcome to Generative AI Mastery, module 2, lesson 2: Project: G S T Invoice Extraction Service.

This is your first portfolio project. You're going to build a small web service that accepts a G S T invoice, either a PDF or a photo, and returns clean, validated J S O N. Here's why it's a great project. Accounts teams at C A firms, distributors and direct to consumer brands spend hours typing invoices into Tally or spreadsheets. So when you show this to an interviewer, they understand the problem straight away.

Let's start with what we're building. The flow is simple. Someone uploads an invoice file to an extract endpoint. A FastAPI app receives it and sends the document to Claude, along with a schema describing the fields we want. Claude's answer is parsed into a Pydantic invoice object. Then our own code runs G S T checks on it. The final response contains three things: the invoice data, a list of any issues found, such as "C G S T and S G S T differ", and a needs review flag that's true whenever there's a problem. The diagram is in the lesson notes below the video.

First, install the dependencies. You need the Anthropic library, FastAPI, the Uvicorn server, python multipart, Pydantic and python dotenv. The exact install command is in the lesson notes. One small detail: python multipart is the package FastAPI needs to handle file uploads, so don't skip it.

Step one is the schema. You create a schemas file with two Pydantic models. The first describes a single line item: a description, the H S N or S A C code if it's printed, the quantity, the unit price before tax, and the taxable value of that line. The second describes the whole invoice: supplier name and G S T I N, buyer name and G S T I N, invoice number, invoice date, place of supply, the list of line items, the taxable total, the three tax amounts, C G S T, S G S T and I G S T, and finally the grand total. A few rules shape this schema. Amounts are plain numbers in rupees. Dates are I S O strings, year, month, day. And anything that might be missing on a real invoice is allowed to be empty. Notice that several fields carry short descriptions, like "zero if not charged" on the tax fields. Those descriptions guide the model. The full code is in the lesson notes below the video.

Step two is the extraction function, in a file called extractor. Here's the key idea: Claude can read PDFs and images directly, so you don't need a separate text extraction step. You send the file itself as a content block, right next to your instruction.

Let's walk through what the code does. It reads the model name from an environment variable, with a sensible default, and creates the Anthropic client. It defines a small set of allowed image types: J P E G, P N G and WebP. Then there's a system prompt. It tells the model it's extracting data from Indian G S T invoices for an accounts team. It says to copy values exactly as printed, convert amounts to plain rupee numbers, use empty values or zero for missing fields, and never invent G S T I Ns, invoice numbers or amounts.

The extraction function takes the raw file bytes and the file's media type. It encodes the bytes as base64. If the file is a PDF, it wraps it in a document block. If it's one of the allowed image types, it wraps it in an image block. Anything else raises an error saying the file type isn't supported. Then it calls Claude's parse method, passing the system prompt, a user message containing the file block followed by the text "Extract this invoice", and the invoice schema as the output format. Finally it checks the result. If the model didn't finish normally, or nothing could be parsed, it raises an error saying extraction was incomplete. Otherwise it returns the parsed invoice. The code is in the lesson notes below the video.

There are three points to note here. First, the file goes in as base64 inside a document block for PDFs or an image block for photos, and the file block comes before the text instruction. Second, we whitelist media types. Never pass arbitrary user uploads through without checking them. And third, we leave the effort setting at its default. Invoices with lots of line items, smudged scans or handwritten notes benefit from a bit more reasoning, and you can tune that later with a test set.

Step three is the G S T sanity checks. Here's the principle: the model reads what's printed, and your code checks whether it adds up. You create a checks file. It defines a regular expression that describes the shape of a valid G S T I N, and a small helper that treats two amounts as equal if they're within one rupee, to allow for rounding.

The main check function builds a list of issues. First, it checks the supplier and buyer G S T I Ns, if present, against that pattern, and flags any that look wrong. Second, it adds up the taxable values of all the line items and compares that with the taxable total. Third, it flags an invoice that charges both I G S T and C G S T or S G S T, because that suggests confusion between inter state and intra state supply. Fourth, it flags C G S T and S G S T if they aren't equal. And fifth, it adds the taxable total and all the taxes, and compares that with the grand total, allowing two rupees of tolerance. The code is in the lesson notes below the video.

These rules come straight from how G S T works. Intra state supplies carry C G S T and S G S T in equal halves. Inter state supplies carry I G S T. And the totals must reconcile. A G S T I N is fifteen characters: a state code, the PAN, an entity number, the letter Z, and a check character. Our pattern checks the shape only. Verifying the official checksum and looking the number up on the G S T portal are good extensions.

Step four is the A P I itself, in a main file. It loads environment variables first, then imports the check and extraction functions and creates a FastAPI app titled "G S T Invoice Extractor". It sets a maximum upload size of ten megabytes. The extract endpoint reads the uploaded file and rejects it if it's too large. It then calls the extraction function. An unsupported file type becomes a clear "unsupported media" error, and an incomplete extraction becomes an "unprocessable" error. If all goes well, it runs the checks and returns the invoice, the issues list, and needs review set to true if there are any issues. There's also a simple health endpoint that just reports "ok". The code is in the lesson notes below the video.

One detail matters. Loading the environment variables happens before the other imports, so the A P I key and model name are already available when the extractor creates its client.

To run it, start Uvicorn with the main app, then open the docs page in your browser. The exact command and link are in the lesson notes. FastAPI generates an interactive page where you can upload a file and see the J S O N come back. That docs page is excellent for demos.

Also note that the extraction function is a normal blocking function called from an async route. For a portfolio demo, that's fine. For real traffic, switch to the async Anthropic client and await the parse call, or declare the route as a plain function so FastAPI runs it in a thread pool.

Now, a privacy note. Invoices contain business names, G S T I Ns and sometimes personal details. For your demo, use sample or self made invoices. Never use a client's real documents without permission. And don't log full invoice contents. Log only the invoice number and the issues list.

Time to try it yourself. This takes about twenty minutes, plus setup. Pause the video and work through these steps. First, create two sample invoices: one intra state, with C G S T and S G S T, and one inter state, with I G S T. A word processor document exported to PDF is fine. Also take a phone photo of a printed one. Second, run the service and upload all three files through the docs page. Third, edit one invoice so the grand total is wrong by five hundred rupees, and confirm that needs review becomes true. Fourth, add a check that the invoice date is a valid date and not in the future. Python's date parsing from I S O format will help. And fifth, commit the project to a new GitHub repository, with your environment file listed in git ignore. You'll deploy it in module 5.

Let's recap. Send PDFs and images as content blocks, and Claude reads them directly. Let the model read and structure the data, and let your code verify it with deterministic rules. A needs review flag turns an imperfect model into a reliable workflow. Whitelist file types and size, and keep sensitive data out of your logs. And FastAPI's docs page gives you a free, demo ready interface.
