Welcome to Generative AI Mastery, module 2, lesson 1: Structured Output and J S O N Extraction with Pydantic.

Most of the business value from L L Ms doesn't come from chat. It comes from turning messy text into clean data your code can use. A lead from an email. Fields from a resume. Line items from an invoice. In this lesson, you'll learn how to get reliable J S O N out of a model, and how to validate it with Pydantic.

Let's start with why just asking for J S O N isn't enough. Beginners write prompts like, return the answer as J S O N. It works most of the time. And then, in production, it doesn't. The model adds a friendly sentence before the J S O N. Or it writes the amount as a string, like twelve hundred rupees with the rupee sign, instead of a number. Or it forgets a field. And your J S O N parsing crashes at two A M.

The robust approach has two layers. First, you constrain the output to a schema, so the model can only produce valid J S O N of the right shape. And second, you validate the result in your own code with Pydantic, and apply business rules that the schema can't express.

So here's Pydantic in two minutes. Pydantic lets you describe data as Python classes with type hints. It validates and converts incoming data, and it can also generate a J S O N Schema from your class. You install it with pip, and the command is in the lesson notes.

The lesson notes then define a class called Lead, describing an enquiry for an edtech company. It has six fields. A name, which is the person's full name. A phone number, which is an Indian mobile number, digits only, or empty. A city, which may also be empty. A course interest, which must be one of four fixed choices: data science, web development, Gen AI, or other. A budget in rupees, as a whole number, or empty. And finally, a yes or no field for whether the person wants a callback. The code is in the lesson notes below the video.

There are three key ideas in that class. First, some fields are marked as optional, meaning they can come back as null. Use this whenever information might be missing, so the model isn't pushed to invent a value. Second, the course interest field uses a Literal type, which restricts it to a fixed list of choices. That's perfect for categories. And third, each field can have a short description. That description becomes part of the schema, and it acts like a mini instruction to the model.

Now let's use structured output with the S D K. The Anthropic S D K has a parse helper. It converts your Pydantic class into a schema, constrains the model's output to match it, and hands you back a validated object. The example in the lesson notes uses a sample enquiry. Rohan Deshmukh from Nagpur says he saw the Gen AI course ad on Instagram, his budget is around eight thousand, and he asks for someone to call him after six P M, giving his number.

The code sends that enquiry with a short system instruction: extract lead details from enquiries for an edtech company, use null for anything not stated, and don't guess. It sets effort to low, and passes the Lead class as the output format. Then it reads the parsed result and prints a few fields, along with the whole lead as neatly formatted J S O N. The code is in the lesson notes below the video.

Here's what's happening. Passing the Lead class as the output format tells the S D K to send the class's J S O N Schema as the required output format. The model's output is then constrained to match that schema, so you get valid J S O N with the right field names and types. The parsed output on the response is a real Lead object. Your editor can autocomplete its fields, and the budget is a whole number or nothing, not a string. Setting effort to low keeps extraction fast and cheap, because this isn't a hard reasoning task. And the instruction to use null and not guess, combined with nullable fields, is your main defence against made-up data.

If you'd rather work with a raw J S O N Schema, for example when the schema comes from a config file, you can pass the schema directly in the output config, use the regular messages create call, and parse the text block as J S O N yourself. But the Pydantic route is easier to maintain.

Next, business validation, which is the second layer. Here's the thing. A schema guarantees shape, not truth. Eight k might come back as eight thousand, which is right. But the phone number might include a country code you don't want. So you add your own checks after parsing.

The lesson notes show a validation function that returns a list of problems. An empty list means the lead is usable. It does three checks. First, if there's a phone number, it strips out everything except the digits, removes a leading ninety one country code if the number is twelve digits long, and then checks that what's left is a valid ten digit Indian mobile number starting with six, seven, eight or nine. If not, it flags the phone as invalid. Second, if there's a budget, it checks that it falls between five hundred rupees and five lakh rupees, and flags it if it's out of range. And third, if the person wants a callback but no phone number was found, it flags that too. At the end, the script prints OK if there are no issues, or the list of problems. The code is in the lesson notes below the video.

In a real pipeline, leads with problems go to a human review queue, instead of straight into the C R M. That pattern, auto accept the clean records and route the doubtful ones to a person, is how most successful extraction systems work in Indian back offices today.

Now let's talk about designing good extraction schemas. The lesson notes have six tips in a table. First, make uncertain fields nullable. That stops the model from inventing values to fill a required field. Second, use enums, the Literal type, for categories, so your downstream code can match on them safely. Third, use numbers for amounts and I S O format strings for dates, so you're not parsing things like twelve hundred rupees, or third March, later. Fourth, add short field descriptions, to clarify units and formats, like rupees as a whole number. Fifth, keep nesting shallow at first. It's easier to debug, and you can add nested models, like invoice line items, once the basics work. And sixth, add a confidence or notes field if it's useful. That lets the model flag ambiguity for human review.

Next, handling failures. Even with constrained output, things can go wrong. The request might be refused, or it might hit max tokens before the J S O N is complete. So check before you trust the result. The short check in the lesson notes raises an error if the stop reason isn't end turn, or if there's no parsed output. Whenever this happens, log the input, minus any sensitive data. Those cases become your test examples later.

What about other providers? OpenAI and Gemini also offer schema-constrained J S O N output, and open-source models served through Ollama support a J S O N format option. The Pydantic validation layer works exactly the same way with all of them. That's one good reason to keep it in your own code, rather than trusting any single provider.

Third, check that missing data comes back as null, and that the unknown course maps to other. And fifth, feed in a deliberately invalid phone number, and confirm that your validation function flags it.

Let's recap. Asking for J S O N in a prompt is fragile, so constrain the output to a schema instead. The S D K's parse helper, given your Pydantic class as the output format, returns a validated Pydantic object. Nullable fields plus do not guess instructions reduce invented data. Schemas guarantee shape, not truth, so add business rule validation and a human review path. And always check the stop reason before trusting extracted data.
