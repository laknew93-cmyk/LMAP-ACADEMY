Welcome to Generative AI Mastery, module 2, lesson 3: Tool Use and Function Calling.

An L L M on its own can't check today's order status. It can't query your database, and it can't do exact arithmetic on five hundred rows. Tool use, also called function calling, fixes this. You describe functions to the model, the model decides when to call them, and your code runs them. In this lesson you'll learn the full round trip.

Let's start with how tool use works. Here's the most important thing to understand: the model never runs your code. The whole flow is a conversation, and it has five steps. First, you send the user's question along with a list of tool descriptions. Second, the model replies with a stop reason of tool use, plus a tool use block. That block names the tool, for example get order status, and gives the input, for example an order I D. Third, your code actually runs that function and gets a result. Fourth, you send back the whole conversation plus a tool result block containing that result. And fifth, the model replies with a normal answer that uses the result. The full flow is in the lesson notes below the video.

Steps two to four can repeat several times in one task. Running them in a loop is what makes an agent, and that's module 4. Here, we'll handle one round cleanly.

Next, defining a tool. A tool definition has three parts: a name, a description, and a J S O N schema for its input. We'll build a support bot for a fictional direct to consumer snacks brand in Bengaluru.

Let's look at what the code sets up. It loads the environment, picks the model and creates the client, just as before. Then it defines a list with one tool, called get order status. Its description says it looks up the delivery status of a customer's order by order I D. It says to use it whenever the customer asks where their order is, when it will arrive, or whether it has shipped. And it explains that order I Ds look like B L R, dash, followed by five digits. The tool is marked as strict. Its input schema has a single required field, the order I D, and doesn't allow any extra fields. Below that, there's a fake database for the demo: two orders, one shipped with Delhivery and an expected delivery date, and one still processing. Finally there's the actual Python function. It cleans up the order I D, looks it up, and returns either the order details or an error message saying no order was found. The code is in the lesson notes below the video.

Here's the thing: writing good tool descriptions is the single biggest lever on tool use quality. There are three habits to build. First, say what the tool does, when to use it, and what the input looks like. Second, write for a smart colleague who has never seen your codebase. And third, use strict mode, together with a required list and no additional properties. That guarantees the model's input matches your schema exactly, so you're not handling missing or misspelt fields.

Now the round trip. The code starts with a small dispatcher function. Given a tool name and its input, it runs the matching Python function and returns the result as a J S O N string. For an unknown tool name, it returns an error instead. Then there's a short system prompt: you're the support assistant for Crunchy Bites, a snacks brand, so be brief and warm. The conversation starts with one user message: "Hi, where is my order B L R one oh two three four?"

The code calls the model with the system prompt, the tools and the messages. If the stop reason is tool use, three things happen. First, it appends the assistant's turn to the conversation exactly as it was returned. Second, it loops over every content block, and for each tool use block it runs the tool and collects a tool result, tagged with that block's I D. All the results go into one single user message. And third, it calls the model again with the updated conversation, so the model can finish the answer. At the end, it prints the text parts of the final response. The code is in the lesson notes below the video.

Let's go through the parts that trip people up. First, when you append the assistant's turn, you append the full content list, not just the text. It includes the tool use block, and any reasoning blocks, which the A P I needs to match your result to the request. Second, each tool result must carry the tool use I D of the block it answers. Third, the model may request several tools at once, for example two order I Ds. Run them all, and return all the results in a single user message. Splitting them across messages confuses the model. Fourth, the tool input is already a Python dictionary, so don't parse it as a string. And fifth, the second call must include the same tools list, so the model understands the history.

Next, reporting errors to the model. If a tool fails, don't crash, and don't silently drop it. Instead, return the error as the result, and mark it with an is error flag set to true. The example in the lesson notes returns a message saying the order lookup service is down, and to ask the customer to try again in ten minutes. The model can then apologise, ask for a corrected order I D, or try another approach. Our order status function already returns a helpful message for unknown I Ds, which lets the model ask the customer to double check.

Now, steering whether a tool is called. By default, the model decides for itself. That's the tool choice setting called auto. On the newest Claude models you can't force a specific tool call, so you steer with the system prompt instead. For example: "Always look up the order before answering any delivery question." Then check in your code whether a tool use block came back. And if you only wanted structured data, not an action, use structured output from the previous lessons rather than a tool.

Let's talk security, because tools are where the risk lives. Once a model can call functions, a malicious user message, or a malicious document, could try to make it call them in harmful ways. There are four ground rules you should already follow, and the table is in the lesson notes. First, validate inputs in your code. For example, check that the order belongs to the logged in customer before returning details. Second, least privilege. A support bot gets an order status tool, not raw database access. Third, confirm before side effects. Refunds, emails and deletions need human or user confirmation. And fourth, limit loops, by capping the number of tool calls per request. We'll return to all this in the safety lesson in module 5.

What about other providers? OpenAI, Gemini and most open source models served through Ollama support function calling in a very similar shape. There's a J S O N schema per tool, a response that asks for a call, and a message that carries the result back. The field names differ, so read their documentation. But your dispatcher function and your security rules carry over unchanged.

Time to try it yourself. It takes about twenty minutes, so pause the video and work through these steps. First, run the example and confirm the bot gives the courier and the expected delivery date. Second, ask about order B L R nine nine nine nine nine, and check that the bot handles the not found result gracefully. Third, ask "Where are B L R one oh two three four and B L R one oh two three five?" and print how many tool use blocks come back. Fourth, add a second tool called get refund policy, with no inputs at all, that returns a short policy string. Then ask, "Can I return an opened packet?" And fifth, ask an unrelated question, like "What is the capital of Kerala?", and confirm that no tool is called.

Let's recap. The model requests tool calls, and your code executes them and sends the results back. Clear tool descriptions, covering what, when and the input format, drive quality more than anything else. Append the full assistant content, match every tool result to its tool use I D, and return all results in one message. Report tool failures with the is error flag instead of crashing. And validate inputs and gate side effects, because tools are your main security boundary.
