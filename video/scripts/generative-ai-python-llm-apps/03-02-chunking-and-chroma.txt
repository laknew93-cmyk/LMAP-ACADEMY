Welcome to Generative AI Mastery, module 3, lesson 2: Chunking Documents and Storing Them in Chroma.

Real documents aren't one line F A Qs. They're forty page PDFs, policy manuals and meeting notes. Before you can search them, you have to split them into chunks, embed each chunk, and store everything with metadata, so you can cite sources later. In this lesson, you'll build that ingestion pipeline with Chroma.

First, why chunk at all? There are three reasons. First, embedding models have an input limit, and text beyond it is simply ignored. Second, a vector for a whole forty page document is a blurry average of many topics, so it matches nothing well. And third, at answer time you want to send the model only the few relevant paragraphs, not the whole file. Smaller, focused chunks mean lower cost and better answers.

Chunking is a trade off, and the table is in the lesson notes. Small chunks of a few sentences give precise matches, but they lose surrounding context, so answers may be incomplete. Medium chunks of a few paragraphs are a good balance for most documents, but they need tuning per document type. Large chunks, a page or more, keep full context, but give blurry embeddings and use more tokens per answer.

Here's a practical starting point. Use chunks of roughly eight hundred to fifteen hundred characters, split on paragraph boundaries, with a small overlap, so a sentence that gets cut at a boundary still appears whole in one chunk. Then tune it using the evaluation set you'll build in lesson 3.4.

Now let's look at the chunker. It's a function that takes some text, a maximum chunk size of twelve hundred characters by default, and an overlap of two hundred characters. The code is in the lesson notes below the video, so let's walk through how it works. First, it splits the text on blank lines to get paragraphs, which are natural units of meaning. Second, it keeps adding paragraphs to the current chunk until the next one would push it over the maximum size. Third, when a chunk is full, it saves it and starts the next chunk with the last two hundred characters of the previous one, so context flows across the boundary. And fourth, a loop handles the special case of a single paragraph that's longer than the limit, by slicing it into pieces. At the end, whatever's left becomes the final chunk.

Libraries such as LangChain and LlamaIndex offer ready made splitters. But writing your own once means you understand what they do, and it's a common take home assignment.

Next, reading PDFs and text files. Install Chroma, pypdf and sentence transformers. The command is in the lesson notes.

The loader function takes a folder and returns a list of records, each with the text, the source file name, and the page number. It goes through the files in the folder in order. For a PDF, it opens it with pypdf, goes through every page, extracts the text, and if the page isn't empty, it adds a record with the file name and page number, counting pages from one. For a plain text or markdown file, it reads the whole file as one record on page one. The code is in the lesson notes below the video.

Notice that we keep the page number with every piece of text. Without it, you can't tell users "see page twelve of the leave policy". And citations are the feature that makes people trust a rag system.

One caveat. Pypdf extracts text, not images. Scanned PDFs need O C R first. Or you can send the PDF pages directly to a model that reads documents, just as you did with invoices.

Now, storing in Chroma. Chroma is an open source vector database that runs inside your Python process and saves to a local folder. You create an ingest file. It loads the same MiniLM embedding model from the previous lesson, opens a persistent Chroma client saved in a folder called chroma D B, and gets or creates a collection called docs, configured to use cosine distance.

The ingest function takes a folder. For every record from the loader, it chunks the text, and for each chunk it builds three things: an I D made from the file name, the page number and the chunk number; the chunk text itself; and metadata holding the source and page. If there are no texts at all, it prints "No documents found" and stops. Otherwise it embeds all the chunks in batches of thirty two, with normalisation, and upserts the I Ds, texts, embeddings and metadata into the collection. Then it prints how many chunks were stored and how many the collection now holds. When you run the file directly, it ingests a folder called docs. The code is in the lesson notes below the video.

There are five key points here. First, the persistent client saves data to disk, so you ingest once and query many times. Second, the cosine setting tells Chroma to use cosine distance, matching how we normalised our vectors. Third, we compute embeddings ourselves, with the same model we'll use for queries. Chroma can embed for you, but doing it explicitly keeps you in control of which model is used. Fourth, deterministic I Ds, built from file, page and chunk, plus upsert, mean that re running ingestion updates chunks instead of duplicating them. If a document shrinks, delete its old chunks first, filtering by source name. And fifth, a batch size of thirty two keeps memory use reasonable on a laptop.

Next, querying. The retrieve function takes a question, a number of results k, which defaults to four, and an optional source file name. It embeds the question with the same model, then asks Chroma for the k nearest chunks. If a source was given, it adds a filter so only that file is searched. It returns a list of results, each with the text, the source, the page and the distance. The code is in the lesson notes below the video.

A couple of details. Chroma returns lists of lists, one inner list per query, so we take the first one. A lower distance means a closer match, because distance is roughly one minus the cosine similarity. And the optional filter restricts search to one file, which is useful when a user picks a specific document.

Time to try it yourself. It takes about twenty minutes, so pause the video and work through these steps. First, create a docs folder with two or three documents. That could be a public PDF such as a state government circular, your college's academic regulations, or a long policy you write yourself, like a leave policy for a fifty person startup in Kochi. Second, save the chunker, the loader and the ingestion code as three separate files, called chunker, loader and ingest, and put the retrieve function in a fourth file called retriever, which imports the embedder and the collection from the ingest file. Then run the ingest file. Third, run retrieve for five questions, and print the source, the page and the first hundred fifty characters of each result. Fourth, change the maximum chunk size to four hundred, and then to twenty five hundred, re ingest each time, deleting the chroma D B folder first, and compare the results for the same questions. And fifth, note which size gave the most useful chunks. Keep those questions, because they start your evaluation set. The exact file names and commands are in the lesson notes.

Let's recap. Chunk documents so each vector represents one focused idea, starting around eight hundred to fifteen hundred characters with overlap. Keep source and page metadata with every chunk, because you need it for citations. Use the same embedding model at ingestion and query time. Deterministic I Ds and upsert make re ingestion safe. And chunk size is a tuning knob, so measure it rather than guess.
