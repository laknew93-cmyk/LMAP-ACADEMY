Welcome to No-Code AI Agents and Automation, module 2, lesson 2: Filters, Routers and Error Handling.

A straight-line workflow is a good start. But real business processes have decisions in them. "Only if." "Otherwise." "If this fails, then." This lesson covers filters, routers, and the error handling that keeps your workflows from failing silently.

Let's start with filters, which decide whether to stop or continue. A filter is a gate. If the condition is true, the run continues. If it's false, the run stops quietly at that point. Zapier calls them Filters. Make attaches filters to the lines between modules. And n eight n uses an If node or a Filter node.

Here are some typical filter conditions. The email subject contains the word "invoice". The order value is greater than five thousand. The city is one of Mumbai, Thane or Navi Mumbai. Or the phone field exists, meaning it's not empty.

Now, write your conditions defensively. Data is messier than you expect. "Mumbai" with a capital M, "mumbai" in lowercase with a trailing space, "Bombay", and "MUMBAI" in all caps are all the same city to a human. But not to a filter. So before filtering, do three things. First, trim spaces and lowercase text in a formatting step. Second, for numbers, make sure the field is treated as a number, not as text. Text comparison can rank nine hundred above ten thousand. And third, decide what happens when a field is empty. Most bugs live there.

Next, routers and branches, which send different cases down different paths. Make calls it a router, Zapier calls them paths, and n eight n uses Switch or If nodes. They all send the run down different branches based on conditions.

Let's look at an example. A pump manufacturer in Coimbatore receives enquiries. Branch A handles enquiries where the product is industrial. Those get assigned to Senthil, with an email and a new CRM deal. Branch B handles agricultural products, which go to the dealer network sheet. And Branch C is the fallback, for anything else, which gets sent to the general inbox for review. The diagram is in the lesson notes below the video.

There are two rules for routers. First, always have a fallback branch. Something will eventually not match any rule, and without a fallback, it just vanishes. Second, make your branches mutually exclusive, unless you really want one item to go down two paths. Some tools run every branch whose condition is true.

Later in this course, AI classification will feed your routers. The AI labels an email as billing, support or sales, and the router acts on that label. For this to work, the label must be one of a fixed list. We'll enforce that in the next lesson.

Now, a quick word on loops and lists. Sometimes a trigger brings in a list. Maybe an order with five line items, or a daily sheet with forty new rows. Tools handle this with iterators or loop steps, which run the following steps once per item, and aggregators, which combine the results back into one. You don't need to master these yet. Just know that when a step seems to run too many times, or only once, list handling is usually the reason.

Now for the big one, error handling. Plan for failure. Every workflow will fail at some point. The Google Sheet gets renamed. An A P I is down for ten minutes. An AI provider rate-limits you. A customer types an emoji where you expected a number. The question isn't whether it fails. It's whether you find out.

There are four types of failure, and there's a table of them in the lesson notes. Temporary failures, like an A P I timeout, a rate limit or a provider outage, are usually fixed by retrying after a delay. Data problems, like an empty phone number or an invalid email, are fixed by validating early and routing to a review sheet. Configuration failures, like a renamed sheet, an expired login or a revoked key, need an alert so a human can fix them. And logic failures, like the AI returning an unexpected label, are handled with a fallback branch and a tighter prompt.

So what tools do you have? There are four. First, retries. Most tools can automatically retry a failed step a few times, with a wait in between. Turn this on for steps that call external A P Is, including AI steps. Second, error routes, or error workflows. Make lets you attach error handlers to modules. In n eight n, you can set an error workflow that runs when any workflow fails, and individual nodes can be set to continue on error. Zapier offers error notifications and some path-on-error options. The names differ, but the idea is the same. When this breaks, do something useful. Third, notifications. Send yourself an email, Slack, Telegram or WhatsApp alert with the workflow name, the step that failed, and the error message. And fourth, a dead-letter sheet. That's a Google Sheet called "Failed items", where any item that couldn't be processed is logged with its data and the error. A human reviews it daily, and nothing is lost.

Next, validate early. The cheapest error is the one you catch at the start. Right after the trigger, add a check. Are the required fields present, and in the right format? If not, send the item to the review sheet and stop. This avoids half-finished runs, where the CRM got updated but the WhatsApp message failed.

And make your steps safe to repeat. If a run fails halfway and you re-run it, will it create a duplicate CRM contact, or send the customer a second message? Use "find or create" patterns, and record a status column, like "WhatsApp sent: yes", that you check before sending. This property, being safe to run twice, will save you a lot of embarrassment with clients.

Now, try it yourself. You'll extend your lead workflow from the previous lesson, and it should take about twenty minutes. Pause the video and follow along. Step one, add a validation step right after the trigger. If the phone is empty or shorter than ten digits, send the row to a new sheet tab called "Needs review", and stop. Step two, add a router with three branches based on city. One for your own city, one for a list of three nearby cities, and a fallback for everything else. Each branch adds a different value in a new Region column. Step three, turn on retries, or the equivalent, for the Google Sheets step. Step four, set up an error notification to your email. And step five, test with four submissions. A valid local lead, a valid nearby-city lead, an unknown city, and one with a missing phone number. Confirm that each one landed where you expected.

Let's recap. Filters stop or continue a run, while routers send it down different branches. Always include a fallback branch, and normalise text before comparing. Expect failures. Use retries for temporary errors, alerts for configuration errors, and a review sheet for bad data. And validate inputs at the start, and design your steps so a re-run doesn't create duplicates or double messages.
