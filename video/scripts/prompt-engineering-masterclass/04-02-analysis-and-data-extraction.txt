Welcome to Prompt Engineering Masterclass, module 4, lesson 2: Analysis and Structured Data Extraction.

AI is excellent at turning messy text into organised information, and at helping you think through data. In this lesson, we'll cover analysis prompts, and a structured data-extraction prompt that you'll test on ten samples as a course project.

Let's start with analysis prompts, and the first one is summarising for a decision. A summary is only useful if it serves a purpose. So tell the model what decision the reader faces. The lesson's example uses forty customer reviews of a Bengaluru cloud-kitchen biryani brand from the last month. The prompt explains that you need to decide what to fix first. Then it asks for three things. First, group the complaints into themes, and for each theme give the number of reviews, one representative quote, and a severity of high, medium or low, with a reason. Second, separately list what customers praise, so you don't accidentally change it. And third, recommend the top two fixes for the next thirty days. It also says: count carefully, and if you're estimating, say so. You'll find the full prompt in the lesson notes below this video.

Next, compare and contrast. Here's the prompt: "Compare the two vendor quotations below for office laptops. Return a table: Item, Vendor A, Vendor B, Difference, Notes. Include warranty, delivery time, payment terms and total cost with G S T. Then list anything one quote includes that the other doesn't mention."

Then there's finding the "so what". Here's the prompt: "Here is our monthly sales data by city. Don't just describe the numbers. Tell me: the three most important changes versus last month, possible reasons for each, labelled as hypotheses, and what data would confirm or rule them out."

A quick word on numbers. Chat models can misread or miscalculate when you paste large tables. Many assistants can now run code or analyse uploaded spreadsheets, and that's far more reliable for calculations. If yours can, upload the file and ask it to compute using code. Either way, spot-check the totals against your own spreadsheet.

Now let's move on to structured data extraction. Extraction means pulling specific fields out of unstructured text, like invoices, emails, resumes, contracts and chat messages. Done well, it saves hours of copy-paste work.

Let's look at an example. Meet Farhan, an operations executive at a Surat textile trader. Every day, he receives order messages on WhatsApp and email, in every possible format. Here's a typical one: "Bhai fifty meter rayon print red wala, same as last time, Sharma Traders Indore, deliver by twentieth, payment thirty days." He needs each order as a row in a spreadsheet.

So here's how the extraction prompt works. It tells the model that it extracts order details from customer messages for a textile trading firm. For each message, it must return one line of JSON with exactly ten fields: the customer name, city, product, colour, quantity, unit, delivery date, payment terms in days, whether it's a repeat order, and a list of things that need clarification. Each field has allowed values, or null if it's not there. For example, the unit can only be meter, piece, or kilogram. Then come five rules. One, use only information in the message, and never guess or fill in typical values. Two, messages may be in English, Hindi, Gujarati-English or Hinglish, so translate the values into English. Three, "same as last time" means it's a repeat order, and the model should add "Confirm previous order specs" to the clarification list. Four, if a quantity has no unit, set the unit to null and add "Unit missing". And five, return only the JSON line, nothing else. Finally, the prompt includes one worked example: an order for two hundred pieces of white cotton dupatta for Mehta Fashion in Jaipur, marked urgent, along with the exact JSON line it should produce. You'll find the full prompt in the lesson notes below this video.

So what makes this prompt robust? There are five things. First, a fixed schema with allowed values. Second, null rules, so the model never invents a field. Third, the needs clarification list, which turns ambiguity into an action item instead of a silent error. Fourth, language handling for real Indian inputs. And fifth, one worked example showing the exact output shape. And if you're working in a spreadsheet, you can swap the JSON for a single tab-separated line with a fixed column order.

Next, testing on ten samples. This is where you apply what you learned in lesson three point three. Build a test sheet with columns for the sample number, the message, the expected output, which you fill in yourself, the AI output, how many fields are correct out of ten, and notes. The layout is in the lesson notes below the video.

Choose your samples deliberately. Use four clean, complete messages. Two with missing information, like no date or no unit. Two in Hinglish or another mixed language. One with two products in one message. And one that isn't an order at all, like "Bhai payment kab tak aayega?" Those last two are where extraction prompts usually fail. So you'll likely need to add two more rules. Rule six: if a message contains more than one product, return one JSON line per product. And rule seven: if the message isn't an order, return a short JSON line that flags it as not an order, with a one-line summary. The exact wording is in the lesson notes.

Then score field-level accuracy. Ten samples times ten fields gives you a hundred checks. Record the score, fix the biggest failure, re-run, and log both versions.

A quick privacy note. Extraction often involves personal or business data. Follow your company's rules about which AI tools are approved. Prefer business or enterprise plans, where the data handling terms are clearer. And remove phone numbers, Aadhaar or PAN numbers, and bank details from any samples you test with.

Now it's your turn. This is the project: Data Extraction, tested on ten samples. Spend about twenty minutes, and pause the video while you work. Step one. Pick a real extraction need, like invoices, job postings, resumes, leads from enquiry emails, or orders. Step two. Design a schema of six to ten fields, with allowed values and null rules. Step three. Write the prompt with one worked example and a needs clarification field. Step four. Collect ten anonymised samples following the mix we just covered, and write the expected output for each. Step five. Run it, score field by field, fix the top failure, and re-run. Log both scores. And step six. Save the final prompt and the test sheet as a portfolio project.

Let's recap. Analysis prompts should name the decision the reader faces, not just ask for a summary. For calculations on real data, use the tool's code or spreadsheet analysis, and spot-check the results. Extraction prompts need a fixed schema, null rules and a worked example. A needs clarification field turns ambiguity into action, rather than silent errors. And test extraction field by field on varied samples, including inputs that don't match at all.
